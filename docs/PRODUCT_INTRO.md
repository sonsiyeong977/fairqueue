## 한 줄 소개

> FairQueue는 플랫폼이 공식 대기열 순번에 따라 발급한 좌석 제안(Offer)을, 사용자가 사전에 위임한 조건과 예산 안에서 에이전트가 자동으로 정산하고, 조건이 성립하지 않으면 예치금을 자동 반환하는 온체인 결제 레이어입니다. 남보다 빨리 사도록 돕는 자동 예매 도구가 아니라, **플랫폼이 공식적으로 부여한 순번·제안에 대해서만 작동하는 B2B 결제 보증 레이어**입니다.
---

## 1. 타깃

### 1차 타깃 — 티켓팅 플랫폼 운영사
- 콘서트, 스포츠, 팬미팅 등 고수요 예매를 운영하는 플랫폼
- 결제 실패로 인한 매출 손실, 매크로 대응 비용, 환불 처리 CS 부담을 안고 있는 사업자

### 2차 타깃 — 최종 구매자(팬)
- 대기열에서 순번을 기다리다 결제 실패로 좌석을 놓친 경험이 있는 유저
- 매진 시 환불이 지연되어 불편을 겪은 유저

## 2. 문제

기존 티켓팅 시스템은 세 가지 구조적 문제를 안고 있습니다.

| 문제 | 설명 | 영향 |
|---|---|---|
| 결제 단계 마찰 | 대기열 순번이 왔을 때 짧은 시간 안에 카드 인증·입력을 마쳐야 해 오류나 지연이 발생할 수 있음 | 구매 기회 상실, 플랫폼의 매출 손실 가능성 |
| 환불 지연 | 매진 확정 후 환불까지 시간이 걸리는 경우가 흔함 | CS 부담, 고객 불만 |
| 매크로/암표 | 비공식 자동화 도구의 대기열 우회 시도 | 지속적인 탐지·차단 비용 |

이 문제들은 서로 연결되어 있습니다. 결제 단계의 불확실성이 클수록 유저들은 더 빠른 수단(매크로)에 의존하려는 유인이 커지고, 플랫폼은 이를 막기 위한 비용을 계속 지출하게 됩니다.

## 3. 솔루션

FairQueue는 유저가 조건과 함께 결제 예상 금액을 **온체인 에스크로에 미리 예치**하게 합니다.

1. 유저가 자연어로 조건(이벤트, 좌석 등급, 최대 가격, 대안 조건)을 입력
2. Gemini가 이를 구조화된 조건(`primary` + `fallback_rules`)으로 파싱
3. 예상 최대 결제 금액을 Solana 온체인에 사전 예치
4. 정상적인 공식 대기열 순서를 그대로 준수 (1계정 1에이전트, 우회 없음)
5. 순번 도달 시 플랫폼이 좌석을 제안(Offer)하면, Gemini가 조건 충족 여부를 1차 판단하고 근거를 제시
6. **결정론적 검증 레이어**가 Gemini의 판단을 코드 레벨에서 한 번 더 확인 — 가격·등급이 실제 조건을 벗어나면 Gemini 판단과 무관하게 강제로 환불 처리
7. 검증을 통과한 경우에만 정산 실행, 그렇지 않으면 예치금 즉시 전액 환불
8. 실결제 금액이 예치 금액보다 적을 경우 차액은 자동으로 유저에게 반환

이 구조에서는 자금이 이미 온체인에 예치되어 있으므로 결제 단계의 시간 압박이 사라지고, 조건 불충족 시에도 정산 요청과 환불 처리가 즉시 이루어집니다.

### 기존 매크로와의 차별점

| | 기존 매크로 | FairQueue |
|---|---|---|
| 대기열 처리 | 우회·편법 시도 | 정상 순서 그대로 준수 |
| 작동 시점 | 좌석을 스스로 탐색·선점 | 플랫폼이 공식 부여한 Offer에 대해서만 작동 |
| 플랫폼과의 관계 | 대립적 (탐지·차단 대상) | 협력적 (매출 손실 방지 인프라) |

## 4. 왜 Solana × Google Cloud인가

**Solana**
- 온체인 예치/정산이 즉시, 저비용으로 이루어져 소액도 부담 없이 예치 가능
- 조건 불충족이 확인되는 즉시 환불 트랜잭션 처리 가능
- 결제·환불·배정 결과가 트랜잭션으로 기록되어 온체인에서 조회 가능
  (대기열 순번 자체는 애플리케이션 상태로 관리되며 온체인 기록 대상은 아닙니다)

**Google Cloud / Gemini**
- 자연어 조건 파싱: 유저의 요청을 1차 조건과 대안 규칙으로 구조화
- 근거 있는 1차 판단: 제안된 좌석과 조건을 비교해 판단과 근거(reasoning)를 함께 생성
- **역할 분리를 통한 안전성**: 실시간 결제 실행이라는 되돌리기 어려운 행위를 LLM 단독 판단에 맡기지 않고, Gemini의 판단은 결정론적 정책 엔진의 재검증을 거친 뒤에만 실행됩니다

## 6. 검증된 구현 (No Mock-up)

아래는 실제 Solana Devnet 트랜잭션과 실제 Gemini API 호출로 end-to-end 검증된 내용입니다.

| 단계 | 검증 내용 |
|---|---|
| 자연어 → 조건 파싱 | Gemini가 유저 요청을 구조화된 조건으로 변환 |
| 플랫폼 API 연동 | Express 기반 좌석 상태 API와 실시간 HTTP 통신 |
| 온체인 예치 | Agent keypair의 사람 개입 없는 자율 서명으로 Devnet 트랜잭션 발생 |
| Gemini 판단 + 결정론적 재검증 | 1차 조건 충족 / 대안 조건 충족 / 매진 세 시나리오 모두, Gemini 판단을 코드가 재검증하는 구조로 검증 |
| 조건별 정산/환불 | 결제 시 판매자 지갑, 환불 시 유저 지갑으로 정확히 분기 |
| 차액 자동 반환 | 예치 금액과 실결제 금액의 차액을 자동으로 유저에게 반환 |
| 부정 패턴 탐지 (PoC) | 요청 로그 패턴을 분석해 매크로/다중 계정 의심 신호를 판정하는 개념 검증 |

## 7. 아키텍처

```
User (자연어 조건 및 최대 예산 입력)
   ↓
Gemini — 조건 파싱 (primary + fallback_rules)
   ↓
Solana Devnet — 예상 최대 금액 온체인 예치 (자율 서명)
   ↓
Official Queue — 공식 대기열 진입, 순번 대기
   ↓ (순번 도달)
Platform Offer — 좌석 제안 발급
   ↓
Gemini — 1차 판단 (조건 충족 여부 + 근거)
   ↓
Deterministic Verification Layer — 코드 기반 재검증
   ↓
   ├─ 검증 통과 → 판매자 지갑으로 정산, 차액 자동 환불
   └─ 검증 실패/매진 → 예치금 즉시 전액 환불
   ↓
Solana Explorer — 결제·환불 트랜잭션 검증 가능
```

## 8. 확장 가능성

- **부정 탐지 고도화**: 현재는 로그 패턴 기반 개념 검증 단계이며, 실제 서비스에서는 IP 외에 디바이스 핑거프린트, 행동 패턴 등 다각도 신호를 결합해 정교화할 수 있습니다
- **온체인 프로그램화**: 현재 MVP는 백엔드가 관리하는 예치 방식으로 구현되어 있으며, 신뢰를 완전히 탈중앙화하기 위해 Anchor 기반 온체인 프로그램(PDA)으로 전환하는 작업을 진행 중입니다
- **적용 범위 확장**: 티켓팅 외에도 한정판 커머스, 예약 시스템 등 "공식 순번·제안 기반의 선착순 거래" 전반에 적용 가능합니다



- **부정 탐지 레이어**: 요청 로그 패턴 분석을 통한 다중 계정 매크로 탐지
- **온체인 프로그램화**: 현재는 백엔드가 관리하는 커스터디얼 에스크로 방식이나, 향후 Anchor 기반 온체인 프로그램(PDA)으로 전환해 신뢰를 완전히 탈중앙화 가능
- **적용 범위 확장**: 티켓팅 외에도 한정판 커머스, 예약 시스템 등 "매진 가능성이 있는 선착순 거래" 전반에 적용 가능
